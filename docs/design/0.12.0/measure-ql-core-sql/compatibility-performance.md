# Compatibility performance against PR #1412

Completed on 2026-10-18: all **80,000 timed RPCs** passed execution and correctness
checks across five paired repetitions. All median point estimates meet the G1
budgets. Six workload/size cases pass with uncertainty included; two small QL
p50 comparisons remain inconclusive. No metric has a confirmed budget regression.
That original campaign remains **inconclusive**. The separate 20-pair
confirmation below passes both uncertain cases under its predefined one-sided
method, closing this matrix’s compatibility follow-up. No production
code was changed or optimized during this comparison.

## Frozen comparison

This compares production revision `012115c56652691d4163f69d0460dfa9b064191f`
(the reviewed PR #1412 base) with `3e68616a0b265a2591654435f1de0dd2d6353a7d`
(Catalog B plus the retained-merge-tail fix). The T01 verification-only revision
`b0a4dc14` has the same production baseline; this comparison does not rerun every
ticket against its immediate prerequisite.

Two isolated worktrees use identical benchmark sources: the 16-file T01 harness,
service-scoped readiness, raw latency recording, and an explicit 256 MiB measure
tracker setting. The overlays change only benchmark files. Production sources,
protobuf and dependencies are unchanged in each checkout. Both executables were
built before timing with Go 1.26.9, without querymetrics instrumentation.

The narrow matrix preserves the recorded T01 workload:

- Input cardinalities: 1,024 and 100,000, returning 64 and 6,300 rows per query.
- Variants: `native`, `native_rebound`, `legacy_ql`, `legacy_ql_rebound`.
- One caller, 1,000 timed calls per variant, profiling enabled.
- Configured warmups: 20. The historical inclusive loop executes 21 validated
  warmup calls; preserved identically on both versions.
- Five paired repetitions; baseline first on odd repetitions and current first
  on even repetitions. Each version/cardinality runs in a fresh process.
- Every container has four CPUs, 8 GiB RAM, no additional swap, and 4,096 PID
  limit. The observed cgroup limits are retained for every timed process.
- One fixture timestamp is pinned across the entire campaign. Both versions
  check independent expected rows and hashes before timing and retain sampled
  full responses for validation after measurement. All timed calls check row count.

Within a process, the four variants run in their historical order and share one
client/liaison/two-data-node cluster. Later variants can observe earlier cache
and heap residency. CPU, allocation and profile observations cover that entire
process, not isolated planning or server CPU. The raw response-retention protocol
is unchanged; adding the recorded latency slice does not add a timed allocation.

The source harness and binary digests are checked before and after each run.
No build or other benchmark ran concurrently. This campaign does not reopen the
stopped historical T02 investigation or benchmark new unsupported SQL against a
fictitious old-version implementation.

## Evaluation method

G1 budgets are unchanged: the ratio of current/base median-of-five p50 latency
and allocated bytes/query must be at most 1.10; p95 latency at most 1.15.
P99, throughput and CPU are reported without introducing new acceptance budgets.
Raw samples and all five run values are retained.

Uncertainty is estimated by paired repetition-level bootstrap: 20,000 resamples,
seed 1412, with the ratio of medians recomputed for each sample. The 95% intervals
are exploratory with only five independent pairs; individual requests are not
treated as independent experimental repetitions. A metric is marked pass when
its entire interval meets the budget, fail when the entire interval exceeds it,
and inconclusive when the interval crosses it. Point-estimate budget checks are
reported separately. This avoids turning an unstable comparison into a pass.

## Small-query confirmation protocol

A separate confirmation campaign follows the five-pair comparison above; those
observations remain unchanged and are excluded from the confirmation estimator.
Before timing, the campaign fixes 20 fresh pairs, with ten baseline-first and ten
current-first pairs shuffled using seed 14120. There is no early stopping or
extension based on observed significance. Only cardinality 1,024 reruns. The
unchanged binaries execute the two native variants before the two QL variants to
preserve historical cache/heap conditions; native observations are supporting
context, not additional confirmation gates. No production or harness rebuild is
needed. CPU, memory, profiling, correctness checks and workload remain identical.

Pilot paired log-ratio standard deviations are 0.0515 and 0.0458. A rough normal
approximation for 80% power at the observed margin below 1.10 suggests 9 and 15
pairs. Twenty pairs are selected before timing. This approximation is only a
sizing diagnostic: it does not establish power for the median-ratio bootstrap,
and the five-pair variance estimates themselves are uncertain.

For each QL variant, compute the ratio of current/baseline medians of 20 run
metrics. Resample the 20 paired indices together 20,000 times with seed 1412.
The empirical 95th percentile is the one-sided 95% upper bound, and the fifth
percentile is the separate one-sided 95% lower bound. These are not a two-sided
95% interval. An upper bound at or below the original budget passes; a lower
bound above it fails; otherwise the verdict remains inconclusive. Budgets remain
1.10 for p50 and allocation, and 1.15 for p95. All three must pass for a variant
to pass; both variants must pass for confirmation acceptance. This all-pass rule
is an intersection-union non-inferiority decision, not a claim of simultaneous
95% coverage for every reported bound. Bootstrap coverage is approximate.

The runner, frozen configuration, analysis and their pre-run hashes are retained
under `.omx/compat-g1-confirmation/`. The original campaign and its two-sided
verdict remain separately recorded; changing the uncertainty method does not
retroactively turn that campaign into a pass.

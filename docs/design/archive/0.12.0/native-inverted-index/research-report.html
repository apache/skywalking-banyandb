01 / THE ANSWER

Replace the engine, preserve the language.

BanyanDB does not need another Bluge. It needs a purpose-built filter-and-sort engine that continues speaking ICE v3 and snapshot v3 while old binaries remain a rollback option.

A

Own the semantics

Query IR, analyzers, numeric terms, snapshots, durability, merge, and administration become BanyanDB code.

B

Keep the binary tongue

Write ice/v3 segments and snapshot v3 until same-file rollback to the legacy reader is retired.

C

Merge live verticals

Build parser and writer evidence on the ticket branch; merge only when one named production role runs natively end to end.

Recommended design

Direct immutable segment builder

Analyze a bounded batch, seal one immutable byte-backed segment, publish a ref-counted snapshot, persist compatible bytes, then merge live content by streaming.

03 / CURRENT SYSTEM

The dependency is wider than one adapter.

Sixteen production files import Bluge packages. Migration, repair, schema reading, analyzers, numeric transforms, and external receive all bypass the nominal store boundary.

1

Terms become FST keys

Raw term bytes map through a serialized Vellum FST to a general posting offset or compact one-hit value.

2

Postings are Roaring

Document numbers use portable Roaring serialization. Different valid container choices can produce different bytes.

3

Stored ≠ sortable

Stored fields preserve original projection bytes. Doc values preserve analyzed terms for sorting and merging. A Store + Sortable field intentionally creates both representations because they are not interchangeable.

4

Compression is implicit

The current fork defaults to S2, but the footer carries no algorithm ID. Historical files must be sampled.

5

CRC is not enforced today

The segment stores CRC32 across every prior byte, yet the resolved ICE loader parses without validating it.

Source observation only. Byte-annotated fixtures and cross-read tests must convert this into the independent specification.

Numbers are widths in bytes. Fixed-width values are big-endian; internal counts and offsets also use unsigned varints.

SEG ≠ SNP

This anatomy describes one immutable ICE .seg file. The Bluge .snp manifest is separate: it chooses the live segment generation and carries per-segment deletion bitmaps. A segment alone does not tell you which of its documents are logically deleted.

01

Stored-field chunks

Recover original field bytes for result projection, migration, repair, and administration. A stored value need not be indexed.

128 documents/chunk → compress([metaLen, dataLen, metadata, data] × document). Metadata repeats (fieldID, valueStart, valueLen) as uvarints; data concatenates the raw values.

Reader: choose docNum / 128, decompress once, then slice the requested values.

02

Stored-field navigation

Find a document inside compressed storage without scanning earlier chunks or documents.

chunk end offsets as uvarints → uint32 encoded-offset byte length → uint32 chunk count → one big-endian uint64 uncompressed offset per document.

Reader: the footer points to the per-document uint64 array; the chunk directory sits immediately before it.

03

Frequency and norm streams

Carry optional scoring/detail data alongside each term hit. BanyanDB mainly needs the document set, but legacy readers may request this detail.

chunk count uvarint → chunk end offsets uvarint[] → compressed uvarints. Each hit records encoded frequency/has-locations plus the float32 norm bits.

Compatibility: a minimal writer must still emit valid streams when legacy merge/query code asks for them.

04

Location streams

Describe where a term occurred. These support phrase/highlight-style detail even though BanyanDB does not require those features.

per hit: location-byte-length uvarint, then repeated (fieldID, position, start, end) uvarints in compressed integer chunks.

Minimal policy: preserve and merge legacy locations; new BanyanDB fields can omit them unless their analyzer contract requires them.

05

Postings records

Answer the central inverted-index question: “which local document numbers contain this field term?”

freqOffset uvarint → locOffsetDelta uvarint → RoaringByteLen uvarint → portable Roaring bitmap bytes. Merge output may instead pack a one-hit doc number and norm directly into the FST value.

Query: AND, OR, and NOT are bitmap/iterator operations over these local document numbers and snapshot deletion masks.

06

Vellum FST dictionaries

Map sorted analyzed term bytes to their postings record quickly, while supporting prefix and ordered term enumeration.

FSTByteLen uvarint → serialized Vellum FST. Values use the top two bits as a tag: 00 means a 62-bit posting offset; 10 means packed one-hit data.

Boundary: term bytes are the compatibility contract; query strings must pass through the same analyzer and numeric term codec.

07

Per-field doc values

Provide a document-to-terms view for explicit sorting, dictionary-like scans, reconstruction, and merge. This is separate from stored fields.

1024-document chunks. Each chunk has doc count + delta(docNum, termEndOffset) metadata and compressed term bytes. Terms use 0xFF separators and 0x5C escaping, followed by chunk offsets and two uint64 trailer values.

Global index: one start/end uvarint pair per field locates these regions; MaxUint64 marks “no doc values.”

08

Field records and fields index

Connect a field name to its term dictionary and record aggregate statistics.

per record: dictionaryOffset uvarint → nameLen uvarint → name bytes → docsWithField uvarint → totalTokens uvarint. The final fields index is one big-endian uint64 record address per field.

Identity: file field IDs are zero-based; ICE forces _id to field 0 and sorts the remaining names.

09

Footer and roots

Bootstrap the entire file from EOF and reject the wrong segment version.

60 fixed bytes, big-endian: numDocs(8), storedIndex(8), fieldsIndex(8), docValues(8), chunkMode(4), timeMin(8), timeMax(8), version(4), CRC32(4).

Caution: version must equal 3. The pinned loader reads but does not verify CRC32, and the footer does not identify the compressor.

10

Compression and chunk mode

Bound decompression and sequential scanning costs without adding a top-level section.

The pinned fork globally defaults to S2. Stored fields always use 128-doc chunks; doc values retain 1024-doc chunks; postings detail chunk size is derived from footer chunk mode 1025 and term cardinality.

Historical risk: compressor choice is process-global and absent from the bytes, so real old segments are required fixtures.

06 / COMMIT LIFECYCLE

A snapshot is the commit record.

A .seg contains immutable data. A .snp decides which segments—and which document numbers inside them—are live.

Admit batch

Normalize identity, analyze fields, apply update/ensure rules.

Publish memory view

Readers atomically acquire a new immutable snapshot.

Persist segment

Write, fsync, close, validate, rename, sync directory.

Publish manifest

Write snapshot v3 with segment metadata and deletion masks.

Callback + GC

Complete durable waiters; later remove unreachable generations.

!

Improvement opportunity: current Bluge writes directly to final names, omits directory fsync, and does not truncate reused IDs. Native temp→rename publication can be stronger without changing final file grammar.

12 / MAINTAINER DECISIONS

Six answers unblock the prototype.

These are product and rollout choices, not details the storage implementation should decide accidentally.

How long must same-file rollback remain?

The report assumes an old binary can open native output throughout rollout.

Which adapter defects become intentional fixes?

Closed-write errors, numeric exact match, negative queries, iterator ownership, and field-universe semantics need labels.

What is deterministic sort order?

Define ties, absent values, repeated values, identity ordering, and pagination keys.

Are epoch and negative timestamps valid?

Current writers omit values at or below zero without a documented contract.

Which batches support durable callbacks?

Series paths honor them; element Batch currently ignores them.

What historical release is the floor?

The answer determines compressors, snapshot versions, analyzers, FST/Roaring versions, and reader scope.

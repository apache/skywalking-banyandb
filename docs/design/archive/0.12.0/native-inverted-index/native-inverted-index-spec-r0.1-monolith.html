01
Stable contract

Defines what the replacement is—and is not.

Contract and scope

The replacement is a BanyanDB filter, projection, and sort engine—not a general-purpose relevance search product.

Requirement language

Marker Review meaning
MUST Required for conformance and release acceptance.
SHOULD Expected unless a reviewed exception records the reason, impact, and replacement control.
MAY Optional behavior that must not weaken a MUST or the compatibility boundary.
fixture gate The stated rule guides the prototype, but production enablement waits for independent byte evidence.
decision gate The corresponding Section 20 disposition must be approved and folded into the next revision.

Objective

SCOPE-001 MUST

Implement the index behavior required by Series, Stream, Property, index-mode Measure, migration, repair, dump, backup, and verification.

SCOPE-002 MUST

Read existing supported BanyanDB index directories and, during the rollback window, emit ICE v3 segments and snapshot v3 manifests readable by the pinned legacy implementation.

SCOPE-003 MUST

Own query semantics, analysis, term encoding, snapshots, durability, merge, external receive, administration, and lifecycle in BanyanDB packages.

SCOPE-004 SHOULD

Retain only low-level codecs whose serialized bytes are already part of the compatibility boundary: Roaring, Vellum, and verified compression implementations.

Non-goals

Excluded capability Reason Compatibility handling
BM25 scoring and relevance ranking No production caller consumes scores. Reader tolerates legacy detail; native query results are unscored.
Phrase/fuzzy/geo queries No required caller identified. Locations may be preserved during compatible merge without exposing APIs.
Highlights, facets, aggregations, explanations Outside BanyanDB index contracts. No native implementation.
General plugin or remote-directory API Would recreate Bluge abstraction surface. Private segment and directory interfaces only.
New disk version during rollout Would break same-file downgrade. Consider only after legacy fallback retirement.

02
Stable model

Defines the immutable objects and three access directions.

Data model and terminology

A logical field may be materialized more than once because filtering, sorting, and returning values travel in opposite directions.

VIEW A · INVERTED term → local documents

Vellum FST dictionaries lead to Roaring postings and optional frequency/location detail. Used for exact, range, prefix, wildcard, and boolean filtering.

VIEW B · DOC VALUES local document → terms

Per-field compressed chunks return analyzed, comparable term bytes. Used for explicit sort, reconstruction, and merge.

VIEW C · STORED local document → source bytes

Compressed document records preserve original stored values. Used for projection, repair, migration, and administration.

INPUT
latency = 120
INDEXED

Numeric terms point to a posting containing local document 0.

SORTABLE

Document 0 points to the shift-zero comparable numeric term.

STORED

Document 0 points to the original value bytes used for return.

≠

Not a duplicate doc value: stored chunks contain original source values; doc-value chunks contain analyzed, escaped term bytes. When one logical field is both stored and sortable, ICE deliberately materializes both representations because they serve different access directions.

Normative terms

Term Definition
Document identity The unique _id term used to find the current live version of a document.
Local document number A dense zero-based number meaningful only within one immutable segment.
Global hit number A snapshot-relative number obtained by adding a segment base offset to a local document number.
Term An analyzer/codec-produced byte string stored as a field dictionary key.
Posting A term's local document set and optional frequency, norm, and location detail.
Stored field Original field bytes explicitly retained for document materialization.
Doc value Analyzed term bytes indexed by document number for sort, merge, or reconstruction; not the original source value.
Segment An immutable ICE v3 byte sequence containing documents and indexes but no logical deletion state.
Snapshot An immutable generation selecting segments and per-segment deletion bitmaps.
Live document A segment document not present in its snapshot deletion bitmap.

ICE v3 segment format

Readers bootstrap from a fixed 60-byte footer at EOF. There is no leading magic. All offsets are absolute from byte zero unless a subsection says otherwise.

Δ

This section is normative for the prototype but remains fixture-gated. A production writer may not ship until independently annotated files and bidirectional cross-read tests confirm every grammar rule.

Primitive encoding rules

uint32 / uint64 fixed width Big-endian.
uvarint 1…10 bytes Unsigned LEB128 as produced by Go binary.PutUvarint; malformed and overflowing values are errors.
offset uint64/uvarint Absolute file address unless explicitly described as a delta, length, chunk-relative offset, or end offset.
term order raw bytes Strict ascending lexical byte order within a field FST.
compression implicit No algorithm identifier exists in the file. Current pinned output uses S2; historical support is corpus-dependent.
version uint32 = 3 The pinned loader rejects every other segment version.

Reader bootstrap

  1. Require file length at least 60 bytes.
  2. Parse the footer backwards from EOF and require version 3.
  3. Validate root ordering, address arithmetic, field-index divisibility, counts, and configured allocation limits.
  4. Skip the reserved CRC32 field; validate structural bounds and codec framing independently.
  5. Load field records, stored chunk navigation, and doc-value readers without decompressing content.
  6. Load FST, postings, or compressed chunks lazily and pin their lifetime to the segment reference.
!

The existing loader parses the footer CRC but does not enforce it. The native reader intentionally retains the field for layout compatibility while neither calculating nor validating it.

Posting-detail chunk size is derived from footer chunkMode. Modes at or below 1024 mean a fixed chunk size. Mode 1025 uses maxDocs / (cardinality / 1024 + 1). Division, zero, and overflow conditions must be bounds-checked.

Posting records and FST values

generalPostingRecord :=
    uvarint(freqNormAbsoluteOffset)
    uvarint(locationOffsetDeltaFromFreqNormOrAbsolute)
    uvarint(roaringByteLength)
    roaringPortableBytes[roaringByteLength]

FST value top-bit tags:
    00xxxxxxxx…  general: lower 62 bits are posting-record absolute offset
    01xxxxxxxx…  reserved; reject
    10xxxxxxxx…  one-hit: 31-bit positive norm + 31-bit local doc number
    11xxxxxxxx…  reserved; reject

The one-hit form is valid only when the term has one document, frequency one, no locations, a positive encodable norm, and a document number fitting 31 bits. The initial native writer may always use the general form if legacy cross-reading proves it valid.

fieldRecord :=
    uvarint(dictionaryAbsoluteOffset)

The fields index begins at fieldsIndexOffset and ends immediately before the footer. Its byte length divided by eight determines the number of field records.

All footer fields are big-endian and appear in the displayed order. The terminal CRC32 field remains a four-byte reserved compatibility slot: native code preserves its position but does not calculate, validate, or use its value. Time bounds preserve signed int64 bit patterns through a uint64 cast.

Fixture gate

The manifest is the commit record and owns deletion state.

Snapshot v3 manifest format

A .seg file is immutable data. A .snp file selects the live segment generation and stores logical deletion bitmaps.

File naming

snapshot final name := lower-case hexadecimal numeric ID, conventionally width 12, + ".snp"
segment final name  := lower-case hexadecimal numeric ID, conventionally width 12, + ".seg"
writer lock         := "bluge.pid" during compatibility window

Readers accept hexadecimal IDs and order them numerically. Temporary/staging names must not match accepted final-name enumeration.

Snapshot v3 grammar

snapshotV3 :=
    uvarint(version = 3)
    uvarint(segmentCount)
    repeated segmentRecordV3[segmentCount]
    uint32BE(reservedCRC32)

segmentRecordV3 :=
    uvarint(typeByteLength)
    typeBytes                         // "ice"
    uint32BE(segmentVersion)          // 3
    uvarint(segmentID)
    uint64BE(segmentSize)
    uint64BE(segmentDocumentCount)
    uint64BE(segmentTimeMinBits)
    uint64BE(segmentTimeMaxBits)
    uvarint(deletionBitmapByteLength)
    roaringPortableDeletionBytes

The final CRC32 field remains at its historical four-byte position but is reserved for compatibility only; native code neither calculates nor validates it. The deletion bitmap contains segment-local document numbers. Length zero means no deletions.

External receive state machine

Stage

Write bounded chunks to an OS/same-filesystem temp file.

Verify transfer

Length, expected hash, retry identity, and completion.

Validate ICE

Version, offsets, FST, Roaring, compression, and limits; retain but do not validate CRC32.

Deduplicate

Optional identity reconciliation under mutation serialization.

Publish file

Sync, validate, rename, and directory sync.

Introduce

Commit a later snapshot containing the segment.

EXT-001 MUST

Validate expected type/version, length, hash, every address, embedded codec, and configured limit before final publication. Preserve but do not validate the reserved CRC32 field.

EXT-002 MUST

Make retry and idempotency explicit; a repeated transfer may not introduce duplicate logical content accidentally.

EXT-003 MUST

Serialize deduplication and introduction with concurrent identity updates and preserve all surviving representations.

Four vertical cutovers replace the live Bluge surface. Each ticket is one reviewable main-branch merge unit.

NIDX-01

Replace the Property shard index

Live Bluge feature replacedproperty/db.newShard selects the native store for existing and new Property shards; Property repair scans use the same native reader.

Inside this ticket

  • Bounded ICE v3 and snapshot readers plus compatible segment/snapshot publication.
  • Property upsert/replacement, delete masks, stored fields, exact/boolean/range filter, and explicit sort.
  • Durable callbacks, snapshots, recovery, merge-time expiry, reference-safe GC, repair scan, and file snapshot.

NIDX-02

Replace the per-segment series index

Explicit boundary

Replace the Stream element index

Open maintainer decisions

These choices must be explicit; the implementation must not decide them accidentally.

Same-file rollback window

DEC-001

Recommendation: retain until one full release after native becomes default and the upgrade/downgrade matrix passes.

Historical release floor

DEC-002

Recommendation: select the oldest BanyanDB release represented by a collected, passing production fixture corpus.

Intentional defect fixes

DEC-003

Approve fixes for closing-write success, numeric exact terms, pure negatives, iterator ownership, and field-universe confusion.

Sort semantics

DEC-004

Recommendation: missing last in both directions, smallest encoded repeated value, identity/local-hit tie key, pinned search-after.

Epoch and negative timestamps

DEC-005

Recommendation: support full signed int64 nanoseconds and stop silently omitting values at or below zero.

Durable callback surface

DEC-006

Recommendation: support callbacks uniformly on element and series batches, with exactly-once terminal completion.

CRC32 compatibility field

DEC-007

Disposition: preserve the historical CRC32 fields only. Do not calculate, validate, cache, or use them for publication, recovery, or corruption classification.

Historical compressors

DEC-008

Recommendation: read only compressors proven by the historical corpus; emit verified S2 during the rollback window.

Resource limits

DEC-009

Recommendation: derive defaults from observed p99 workloads with explicit overrides and hard safety ceilings.

Identity sort support

DEC-010

Recommendation: specify and implement it only if a production planner contract is confirmed; otherwise reject it explicitly.
